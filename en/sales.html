scale with care

WoowTech · EMQX 5.8.9

Compare features and scale before you talk adoption

This handbook helps you run the discovery call, take stock of requirements, compare EMQX with the Mosquitto built into Home Assistant, and plan a phased rollout and acceptance. EMQX 5.8.9 is an open source MQTT broker, not a platform that does everything; this page makes no inflated performance promises, and lists only the gaps you can verify and the next step you can take.

What to ask in the discovery call

Requirements inventory

  • How many MQTT clients and subscriptions do you have today, and how many do you expect a year from now?
  • Is the message volume a few hundred a minute, or do you need a high-throughput device backbone?
  • Do you need the Rule Engine, data egress (Connector/Sink) or bridging across brokers?
  • Is there only one Home Assistant host, or do you want room to grow into a cluster with several nodes?

Current setup and ownership

  • Are you on the Mosquitto built into Home Assistant today? How long a downtime window does the migration get?
  • Who maintains EMQX, backs up /data/emqx and rotates the certificates?
  • Are Zigbee2MQTT, ESPHome or other clients already connected to some broker?
  • Will the admin Dashboard be opened from the local HA, or does it need a URL of its own?

Where EMQX and Mosquitto each fit

The Mosquitto built into Home Assistant is an entry-level broker that is good enough for the basics; EMQX 5.8.9 is a message backbone you can grow, manage and integrate. Both speak MQTT. The difference is in the admin surface and in how far each one can be extended.

AspectMosquitto (built into HA)EMQX 5.8.9
InterfaceOptions on the HA integration screen, plus entries written into the HA config fileA full Dashboard: users, ACL, Listeners, rules and monitoring on one screen
Authentication and authorizationMostly whatever the general-purpose settings give youPassword-Based Built-in Database, JWT, HTTP/LDAP authentication concepts, plus ACL topic rules
Rules and Data IntegrationYou write your own code outside the brokerA built-in SQL Rule Engine, Actions (republish/console), Connector/Sink/Source
Monitoring and operationsBasic status only, leaning on the HA sideOverview, Metrics, the client list, Log & Trace, RBAC (Enterprise only), Health Check
Best forGetting started, with a fixed set of standard subscriptionsMany clients, where you need rules, monitoring and room to grow
How to say it: say "EMQX adds these capabilities on the admin, rules and monitoring side." Do not say "Mosquitto is bad" or "EMQX is bound to be faster." Performance and scale come down to acceptance testing under your real load.

Sizing

Scale is not just the total device count. Record the number of clients, the number of subscriptions, the size of each message, retained messages, how often rules match, the connection rate and the resources on the HA host as well. What EMQX 5.8.9 can actually take is decided by the number of Listeners you create, by QoS, by the subscription load and by the hardware. Load-test with a representative data set first, and do not extrapolate one successful run into a guaranteed ceiling.

SignalWhy it matters
Clients and subscriptionsSets the load from sessions, keepalive and ACL rules.
Message rateTells you whether the gateway is falling behind, or the Rule Engine is the busy part.
Retained messagesA large number of retained topics costs memory and weighs on the topic tree.
Rules and ConnectorsThe throughput and latency of SQL rules and an HTTP Sink are a separate layer.
Persistence layerMemory, disk and network on the HA host are the bottleneck everything shares.

Suggested rollout phases

  1. Discovery and baseline: pin EMQX 5.8.9 and add-on 5.9.0, then take stock of the existing broker, of who owns the migration, and of the feature list.
  2. Lab pilot: use a handful of developer tools, or test publish/subscribe traffic, to verify the Dashboard, authentication, ACL and rules.
  3. Same-network migration: move the important existing HA subscriptions to EMQX one at a time, verifying Zigbee2MQTT, QoS and will messages as you go.
  4. Phased cutover: switch over in batches by area or by risk, and keep a backup, a restore point and a change record for every batch.
  5. Handover to operations: hand over backups, certificate rotation, the monitoring baseline, upgrades, the split of responsibilities and a regular re-check.

Security and data boundaries

  • MQTT passwords, client IDs, usernames, API keys, ngrok authtokens, TLS private keys and connection strings always go in as placeholders; they never reach the HTML, a log or a commit.
  • Do not expose the Dashboard admin surface straight to the internet; use Home Assistant's "Open Web UI" Ingress, or another proxy that keeps exposure minimal.
  • Before you open 1883 to the outside, spell out the risks of a public broker and the TLS requirement; keep the Rate Limit and the permissions minimal.
  • Setting up authentication on first use is the lowest boundary, not protection against everything, and should never be described that way.
  • Backup scope = /data/emqx (data, ACL, authentication and rule settings); say what it affects before you restore.

Acceptance checklist

Feature acceptance

  • The Dashboard shows EMQX version 5.8.9; the add-on shows 5.9.0.
  • An MQTT user created in the Dashboard can connect with authentication.
  • ACL topic rules take effect on a least-privilege basis, and denials show up in the logs.
  • One rule fires successfully into console output, and then forwards to a Sink.
  • After the move off the Mosquitto built into HA, the existing subscriptions are still there.

Operational acceptance

  • A backup can be restored from /data/emqx.
  • Any externally facing Listener has TLS configured, or is explicitly left closed.
  • The monitoring baseline (Clients, messages, node resources) has been recorded.
  • There is a runbook you can actually follow for port conflicts, an unstable gateway and authentication failures.
  • Gaps against Mosquitto, and anything not yet accepted, are listed as exceptions.
